# Decisions

Each decision with its status, the evidence and the alternatives considered.

## D0. Repository method: release tarball + patches + overlay (as the sibling ports)

**Status:** approved by the user (2026-10-08, plan).

The signed PHP release tarball pinned in `upstream.conf` (SHA-256 and the release manager's
GPG key in `keys/`), `patches/` applied in `patches/series` order, `overlay/` (add-only),
`staging/` generated by `tools/prepare.sh`, remote work through `tools/vms.sh`.

## D1. PHP version: 8.5 (latest), with 8.4 or 8.3 as fallbacks

**Status:** approved by the user (2026-10-08).

PHP 8.5.11 (24 Sep 2026), signed by Volker Dusch (`49D9AF6BC72A80D6691719C8AA23F5BE9C7097D4`,
from php.net's keyring). phpBB 3.3.19's `docs/INSTALL.html` lists PHP 7.2 "up to and
including PHP 8.3"; if phpBB fails on 8.5 in acceptance, the same port is re-pinned to 8.4 or
8.3 (the patches should mostly carry over). 8.5 adds two always-built extensions, `lexbor`
(bundled HTML/URL parser) and `uri`, and builds opcache in.

## D2. Compiler: clang (LP64) on x86-64

**Status:** approved by the user (2026-10-08, plan); x86-64 only for the first kit.

PHP's 64-bit build assumes `size_t` and pointers have the same width and uses GCC builtins
and `__atomic`; it needs C99 (C11 features optional). clang on x86-64 is LP64 with all of
these (vms-mariadb D4). VSI C on x86-64 is ILP32 with a 32-bit `size_t`: PHP would be a
32-bit build (32-bit integers, 2 GB limits) and lose the builtins. clang also allows the
HYBRID Zend VM (computed goto). Reused from vms-mariadb: `__GNUC__` defined in the clang
flags, the forced-include header for the C RTL's 32-bit `long` interfaces (D12), the
`LIB$INITIALIZE` feature logicals (D6).

Alternatives: VSI C (32-bit PHP, as the existing third-party kits; shares the vms-zlib,
vms-pcre2 and SSL3 `_SHR32` ABI, and would cover IA64) - rejected for x86-64; it stays the
route if IA64 is wanted later.

## D3. Extensions: static, the phpBB set

**Status:** approved by the user (2026-10-08, plan).

Built in (no `dl()`): the always-on set (Core, date, hash, json, lexbor, pcre, random,
Reflection, SPL, standard, uri, opcache) plus ctype, dom, filter, libxml, mbstring
(`--disable-mbregex`: no oniguruma), mysqli + mysqlnd, openssl, session, SimpleXML,
tokenizer, xml, xmlreader, xmlwriter, zlib. phpBB 3.3's hard requirements are json and
mbstring; its bundled libraries add dom and filter (s9e/TextFormatter), mysqli for the
board's database, openssl for SMTP over TLS. Not built: pdo, phar, gd (no image CAPTCHA or
thumbnails at first: user, 2026-10-08), intl, iconv, curl, sockets, posix, pcntl.

## D4. Dependencies: clang builds of the family's libraries

**Status:** approved by the user (2026-10-08, plan).

zlib: a clang (LP64) variant in vms-zlib (as vms-pcre2's for vms-mariadb D11); PCRE2:
vms-pcre2's clang tree (not PHP's bundled copy; JIT off); libxml2: a new sibling repository,
vms-libxml2; OpenSSL: VSI SSL3's 64-bit-pointer images with an audit of the `long`-typed
calls ext/openssl makes (vms-mariadb D9), our own OpenSSL build as the fallback.

## D5. Process model: no fork

**Status:** approved by the user (2026-10-08, plan).

The CGI SAPI runs as a FastCGI server (`-b`, `PHP_FCGI_CHILDREN=0`), one process per pool
member, exactly as vms-lighttpd's `PHP_POOL.COM` runs PHP today. `proc_open`, `pcntl` and
`mail()` are unsupported in the first kit; phpBB sends mail over SMTP.

## D6. Naming

**Status:** approved by the user (2026-10-08, plan).

PCSI product PHP (producer ISSINOHO), logical name `VMSPHP$ROOT`, images
`[BIN]PHP.EXE` and `[BIN]PHP_CGI.EXE`, settings `[ETC]PHP.INI`, `VMSPHP$STARTUP.COM`.
vms-lighttpd's pool takes the PHP root logical as a setting (`vmslighttpd_php_root`).

## D7. SSL3's 32-bit `long`: a forced-include header for ext/openssl

**Status:** approved by the user (2026-10-08, Phase 0 exit).

ext/openssl calls 14 `long`-typed SSL3 functions (docs/PHASE0.md). A header force-included
into ext/openssl's compiles redefines the five `long`-returning ones as sign-extending
wrappers (`#define BIO_ctrl(...) ((long)(int)BIO_ctrl(...))`, the same for `SSL_ctrl`,
`SSL_CTX_ctrl`, `SSL_CTX_callback_ctrl`, `SSL_get_verify_result`) and wraps `NCONF_load` /
`NCONF_get_number_e` with `int`-sized temporaries. `unsigned long` returns and small `long`
arguments need nothing. Alternatives: patching each call site (24+ places, fragile on
re-pin); our own OpenSSL built with clang (large; the fallback, as in vms-mariadb D9).

## D8. Entropy for random_bytes(): OpenSSL RAND_bytes

**Status:** approved by the user (2026-10-08, Phase 0 exit).

VMS has no `getrandom`, `getentropy`, `arc4random` or `/dev/urandom`, and
`SYS$GET_ENTROPY` is not present on E9.2-4 (`CALLUNDEFSYM`). A patch to
`ext/random/csprng.c` (`php_random_bytes`) takes bytes from SSL3's `RAND_bytes` on VMS
(OpenSSL seeds itself from the system). ext/openssl links SSL3 anyway (D3).
Alternative: a home-made pool from `$GETTIM`/`$GETJPI` values (not cryptographic).

## D9. max_execution_time: ITIMER_REAL / SIGALRM

**Status:** approved by the user (2026-10-08, Phase 0 exit).

`<signal.h>` has no `SIGPROF`; `setitimer(ITIMER_REAL)` delivers `SIGALRM`. A patch makes
`zend_set_timeout_ex` use the real-time timer on VMS, as PHP already does on macOS on
Apple Silicon (wall-clock time, not CPU time, counts towards the limit). The probes showed
that jumping out of a signal handler ACCVIOs on VMS; PHP's handlers never do (the hard
timeout writes its message and exits).

## D10. Fibers: Boost.Context's x86-64 SysV routines

**Status:** approved by the user (2026-10-08, Phase 0 exit).

`Zend/asm/{make,jump}_x86_64_sysv_elf_gas.S` assemble with VSI clang and switch contexts
correctly under the VMS calling standard (probe `r_fiber`). They reference `_exit` (reached
only if a fiber's entry function returns); an overlay shim supplies it. Alternative:
fibers disabled (`Fiber` throws) - not needed.

## D11. C RTL `long` interfaces and process exit codes

**Status:** approved by the user (2026-10-08, Phase 0 exit).

`%ld`/`%zu` and `strtol` in the C RTL are 32-bit: vms-mariadb's forced-include
`vms_lp64.h` (D12 there) for all of PHP. `popen`/`system` work, but report DCL's success
status (1) as exit status 1: `exec()`/`system()`/`passthru()` map a VMS status to 0
(success, odd) or 1 (failure) on VMS. `proc_open` stays unsupported (no fork; D5).

**How the status is obtained** (approved by the user 2026-10-10; PORTING_LOG #35): pclose()
cannot be used, since it loses the status altogether (probe `r_pclose_status`: `exit 1` and `exit 2`
both come back as 0). Patch 0012 runs the command as `PIPE cmd ; WRITE SYS$OUTPUT
marker,$STATUS`, and a read filter takes the marker line off the end of the output (probe
`r_exec_status`). A C program's `exit(n)` arrives as `%X0035A001 + n * 8`, an odd status
that the plain odd/even rule would call success, so it is decoded back to n. Any other status
maps to 0 if odd, 1 if even. Alternatives considered:
- Return the status through a job logical name (`DEFINE/JOB` in the PIPE). This keeps the
  output untouched, but apostrophe substitution does not happen inside the PIPE segment, so
  the name received the literal `'$STATUS'`.
- Write the status to a temporary file: one more file per call, plus cleanup.
- Document the result code as unreliable on VMS.
Known limits:
- A command that ends DCL itself (`EXIT n`) prints no marker, and pclose()'s value is kept.
- A command with `|` or `(` outside quotes runs unwrapped and keeps pclose()'s value. Under popen,
  output from a PIPE segment that follows a pipeline or a subshell is lost, and `(a | b) ; c`
  hangs in the subprocess (probe `r_popen_pipe`).
- A command that prints its own marker as its last line, and then stops DCL, can spoof the
  status.
- DCL has no `echo` verb, so Zend's bug80811 still fails, now with result code 1 (`%DCL-W-IVVERB`).

## D12. phpt tests run without file-protection privileges

**Status:** approved by the user (2026-10-15).

The account that runs the tests on the node holds SYSPRV and READALL, and those override file
protection: is_readable(), is_writable() and is_executable() return true after chmod(0), and
writes into read-only directories succeed. The Linux reference runs without root. So
tools/vms_phpt.com drops SYSPRV, BYPASS, READALL and GRPPRV for its own process before running
the tests. This also matches the board, whose PHP should run as an unprivileged account; that
gets checked in Phase 3. Alternatives considered:
- A separate unprivileged test account. Setting one up would need the user to act on the node.
- Recording the privilege-dependent tests as expected differences. This would hide real
  protection bugs.

## D13. Files PHP rewrites keep a single version

**Status:** approved by the user (2026-10-10; PORTING_LOG #40).

On OpenVMS each rewrite of a file with `fopen(..., "w")` or `file_put_contents()` creates a new
version, and so does `rename()` onto an existing file. phpBB rewrites its cache and store files,
so those would accumulate versions up to the 32767 limit. Two changes keep one version:
- Patch 0015: an existing file opened with "w" is truncated in place, which is what POSIX does.
- `vms_php_rename` deletes the target's versions before renaming. The target is briefly
  absent, where POSIX's rename() is atomic; phpBB's cache treats a missing file as a miss.

Alternatives considered:
- Keep the C RTL's behaviour and set `SET DIRECTORY/VERSION_LIMIT=1` on phpBB's writable
  directories at install time. This needs a step at deployment, and it applies only to the
  directories that step covers.
- Purge the older versions after each write or rename. That needs VMS file specifications
  (the C RTL's UNIX names cannot name a version), and the versions would exist until the purge.

## D14. The mysqli tests move to Phase 4

**Status:** approved by the user (2026-10-10, Phase 2).

The plan lists the mysqli `.phpt` set in Phase 2, run against vms-mariadb. That project's test
server (port 3307) has not run since the node was rebooted, and starting it belongs to vms-mariadb.
Phase 4 runs mysqli through phpBB against a running server anyway, so the set runs there,
together with the board tests. Phase 2 covers mysqli only by building and loading the extension.
The host has no MySQL server, so there is no Linux reference run for mysqli. Alternatives
considered:
- Start vms-mariadb's server for Phase 2, in its own test database.
- Run the set against the board's database. No: the board is the user's.
